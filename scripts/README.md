# scripts

The repository's build, generation and check tooling. Every script is run through a script of the
root `package.json`, except `dist-manifest.mjs`, which each dist-published package runs from its own;
`inputs.config.mjs` and `lib/` are modules the others import. The commands below are those script
names. The scripts carry no comments (`LINT.md`), so what a maintainer needs to know about why each one
works the way it does is written here.

The `*.test.mjs` files beside them are `node --test` suites, run by `npm run test:scripts` and so by
`npm test`. The `*.allow.json`, `*.snapshot.json` and `*-baseline.json` files are the committed state
some checks hold the code to; each allow-list entry carries its reason as its value, and every check
that reads an allow-list fails on an entry that no longer matches anything, so the lists only shrink.

## gen-inputs.mjs and inputs.config.mjs

`npm run gen:inputs` writes each kernel's inputs namespace (`occ-inputs.ts`, `jscad-inputs.ts`,
`manifold-inputs.ts`, `ifc-inputs.ts`, `verb-inputs.ts`) from the fragments in the directory beside it;
`npm run check:inputs` (part of `npm test`) writes nothing and fails when a committed file is not what
its fragments assemble to, naming the first differing line.

- A namespace of 60 to 300 DTO classes has to stay one compilation unit: TypeScript cannot merge a
  namespace across modules, and the declarations downstream tooling is generated from are matched on
  the innermost namespace name. Only the authoring is split. Each fragment is a slice of the namespace
  body, unindented, with its own imports so it reads and type-checks as an ordinary module; the
  generator drops those imports, indents the body by four spaces and wraps it in the namespace, under
  the target's `header` and a `// GENERATED by` line.
- A fragment's header is optional. When the file opens with `// ` or `import` lines, that run is the
  header and a blank line must follow it; header and blank line are dropped. A file that opens with
  anything else - its first declaration or JSDoc, as a fragment without imports may - has no header
  and is all body. A blank first line is still read as an empty header's separator and dropped, so a
  fragment written either way assembles the same. A `//` line after the separator is body and survives.
- `namespace.ts` in each directory holds only the namespace's JSDoc block (with or without a header),
  which is placed directly above `export namespace`.
- `inputs.config.mjs` names the four targets and their fragment `order`. The order is explicit on
  purpose: the emitted `.d.ts` follows it, so it is part of what consumers read, and leaving it to the
  file system would let a rename reorder a published declaration file. A fragment named there must
  exist and a fragment in the directory must be named there; the generator fails on either, so a new
  file cannot be quietly left out.
- `targets` is also read by `eslint.config.mjs` (the assembled files are not linted),
  `packages/dev/vitest.shared.ts`, `lib/surface.mjs` and `check-api-docs.mjs`. `fragmentNote(dir)`
  builds the two-line note a fragment header may carry.

## dist-manifest.mjs

Run from a package directory by that package's `copy-package` script (part of `build-p`). It derives
the manifest npm publishes from the package's own and writes it to `dist/package.json`, refusing a
manifest that could only resolve inside this workspace. It also writes `dist/.npmignore` with
`*.tsbuildinfo`: the build info lives in `dist/` so that deleting `dist/` deletes it too (`tsc -b`
trusts it over the outputs when deciding a project is up to date), and npm must not ship it.

The published manifest drops three fields (`DROPPED_FIELDS`):

- `exports`. Every source manifest carries the map `expectedExports` derives from the package's tree,
  with the `@bitbybit-dev/source` condition first in each entry: a consumer that declares the condition
  resolves the TypeScript sources (each package's test configuration does, so a suite sees a sibling's
  edit without a rebuild), and one that does not resolves `dist/`. TypeScript, esbuild and Vite resolve
  an exports target as the exact file it names, so the map spells out every subpath imported without
  an extension, and maps the rest by pattern: an extensionless request to the `.ts` source, a `.js`
  request to the module of that name. A published package keeps resolving through `main` and `types`,
  as every version so far has: an exports map in the tarball would refuse the extensionless deep
  imports the examples and users' projects make, which `check-tarballs.mjs` probes exactly that way.
  The condition name never leaves this repository.
- `devDependencies` and `scripts`, which describe building and testing this tree, not using the
  package.

`expectedExports` lists exact entries first, because they win over patterns: the root, every
directory index under `lib/`, every kernel module, every JavaScript module at the package root (the
generated jscad module), then the patterns. In a kernel directory only a compiled `.js` with
hand-written typings beside it counts. A root module is taken on its own, because `tsc` emits its
typings into `dist/`, where `types` points; requiring a `.d.ts` beside the source would leave the
extensionless subpath resolving under every condition but the source one.

`manifestProblems` refuses:

- a `repository` other than `{ type: "git", url: "git+https://github.com/bitbybit-dev/bitbybit.git",
  directory: "packages/dev/<name>" }`. npm provenance compares the published manifest's
  `repository.url` against the repository the publish workflow runs in, so a URL with a `/tree/...`
  path or in another form fails the publish after the tarball is built;
- a `workspace:`, `link:`, `file:` or `portal:` specifier: siblings link through exact pins, and pnpm
  would not rewrite such a specifier on the way out of `dist/`;
- an exports map other than the derived one, and a package without `index.ts` at its root.

## gen-exports.mjs and check-exports.mjs

`npm run gen:exports` writes each dist-published package's exports map from its tree, using
`expectedExports` from `dist-manifest.mjs`. Run it after adding a directory index under `lib/`, a
kernel module or a root JavaScript module. The rest of the manifest is untouched: the map is placed
after `"types"` and the file keeps its indentation.

`npm run check:exports` (part of `npm test` and `verify.yml`) needs no build. It holds every source
manifest of the packages `tsconfig.build.json` references to `manifestProblems`, and every built
`dist/package.json` to be byte for byte what the derivation writes, so a stale or hand-edited
published manifest fails here rather than in `npm pack`.

Both read the package list from the references of `tsconfig.build.json`, as `check-tarballs.mjs` and
`check-strict-baselines.mjs` do, dropping `//` lines first because a tsconfig may carry comments.

## check-api-docs.mjs

The state of the JSDoc on the public API, held to `api-docs-baseline.json`. That JSDoc is what a user
reads - the published declarations carry it into the editor, the documentation pages and the editor
tooltips and their translations derive from it - and `API_DOCS_GUIDE.md` says how it is written. The
script reports where the corpus falls short of the guide, per file and per rule, and never writes a
source file: the JSDoc is structured metadata that generators read, and only a person rewrites it.

- `npm run check:api-docs` (part of `npm test`) compares the counts with the baseline: a count may only
  fall, a fall must be recorded, a stale entry fails.
- `npm run api-docs:report` lists every finding by file; `--json`, `--rule <id>`, `--package <name>`,
  `--path <prefix>` and `--info` filter or reshape it.
- `npm run api-docs:update` rewrites the baseline and takes no other flag.

Kinds: M public method, C API class, D inputs DTO class, P DTO property. Severity (`SEVERITY`): error
means a consumer breaks or misrenders and is driven to zero first; warn is depth, ratcheted; info is a
review candidate, printed by `--report --info` and never baselined.

What is walked:

- `ROOTS` are walked as the runtime resolves a dotted path: each kernel from its service class, each
  renderer from its facade (`BitByBitBase`), which reaches base, core, the worker mirrors and the
  renderer's own classes. A class is followed through a field's type, or each side of an intersection.
  The generated worker mirrors are walked through but not audited - they are generated from the
  kernels and audited there - and neither are the deprecated verb classes. `SKIP_FIELDS` are facade
  fields that are infrastructure or deprecated.
- A constructor parameter property is not followed: it is wiring (a helper, the context) that the
  published declarations drop with the constructor.
- The hand-written worker members (`HAND_DIRS`, `HAND_FILES` in `lib/surface.mjs`) are audited file by
  file; a member marked `// replaces` without a doc inherits the kernel's.
- DTOs are read from the fragments and hand-written inputs files, never from the assembled namespaces.

Rules worth knowing the reason for:

- `unsafe-description`: an `@` cuts a generated tooltip there; docs are markdown rendered to text, so
  no headings, links, tables, HTML or underscore emphasis; `*` is neither a bullet nor multiplication.
- `wrapped-list-marker`: a wrapped line that starts with `-`, `+`, `*` or `1.` renders as a list item.
- `forbidden-words` (`FORBIDDEN`): a library doc names no product built on the library and no editor or
  implementation term, and a few recurring typos.
- `doubled-word` is info only: "the the" is usually a slip, but a term such as "mesh mesh intersection"
  or a quoted example is not.
- `stray-tag` on `@default`: the generators parse a default as JSON exactly when it holds `[` without
  `+` or `{` without `{0}` (`generatorsReadAsJson`), so such a default must be valid JSON.
- `default-mismatch`: the initializer and `@default` are two authors of one value - `new Dto()` runs
  the first, tools that read the declarations read the second - so they must agree. An enum member agrees with its
  name or its value; a string property takes the tag as text however it reads (the generators
  stringify a number), and `\n` written as two characters in the tag stands for a line break, since a
  JSDoc line cannot hold one. Enum values are read as TypeScript numbers them (a member without an
  initializer is the previous number plus one); a computed one is unreadable and not compared.
- `optional-mismatch`: `?` lets a script leave a property out; `@optional true` lets a generated
  component leave its input empty. A property with a `@default` value gets it from the component's
  control and needs no `@optional`; one with neither must say `@optional true`, or the component gates
  on it while a script may omit it.
- The spelling rules. A DTO property is one of three kinds, each with one spelling:

  | Kind | Spelling | Meaning |
  |---|---|---|
  | required | `x!: T;` | no initializer; a caller must pass it |
  | defaulted | `x?: T \| undefined = d;` | the initializer is the default, and `@default` repeats it |
  | optional | `x?: T \| undefined;` | `@optional true`; left unset, it stays unset |

  `new Dto()` runs the initializer and nothing else sets a default, so a `@default` without one exists
  only in the documentation. `| undefined` is written out because an inferred type prints differently
  under different compiler flags, and because under `exactOptionalPropertyTypes` only that spelling
  lets a caller pass an optional value straight on. A defaulted property without `?` is still
  required in an object literal; `defaulted-spelling` ratchets that down rather than forbidding it,
  and counts it only on a class some method takes (as a parameter, or held by a property of one it
  takes, through type aliases and parents): a class that is only returned carries its initializers as
  placeholders. A constant tag (`type = "arc" as const`) is not a default.
- The constructor rules: every constructor parameter names the property it fills, spelled the same, or
  it is a public signature nobody can call by name; a required parameter means `new Dto()` does not
  type-check; a parameter property is refused because the spelling, default and constructor rules
  never see the property it declares.
- `pair-parity`: a singular DTO and its plural in the same file (`XDto` beside `XsDto`, `XesDto`,
  `XShapesDto` or `XCentersDto`, or a name of several words with both its first and last word plural)
  describe the same setting, so a property both have, declared or inherited, agrees on its type,
  default, bounds, step and `@optional`. Where the two share a property through an abstract parent
  there is nothing to compare. A difference is reported on the plural's declaration.
- A DTO's parent is the class its `extends` names in the namespace the qualifier names (or its own),
  nearest first: the same file, as TypeScript scopes an unqualified `extends`, then the same
  directory, the same package, anywhere. Two candidates at the nearest distance are an error.
- `missing-example` (info) counts the properties of the DTO a method takes, matched by namespace and
  along the method's package's inputs chain (`INPUTS_CHAINS`), parents included and pointer-like
  properties left out.
- `duplicate-description` and `sibling-echo` (info): the same sentence on two members of one class, and
  a property description that starts with a word from a sibling property's name and none from its own.

## check-resolved-entry.mjs

`npm run check:resolved-entry` (part of `npm test`; `--verbose` also prints every method checked) fails
when a public method takes a DTO with defaults and does not lay its inputs over them first.

Only `new Dto()` runs a DTO's initializers, and a caller - a script's object literal, a message from a
worker, a server request - rarely builds one: it passes a plain object that leaves defaulted
properties out or sets them to undefined. So such a method starts with
`const resolved = resolveDto(Inputs.X.Dto, inputs) as Resolved.X.Dto;` and reads only `resolved`
afterwards (`packages/dev/CLAUDE.md`). One more read of the raw inputs loses the default again for that
property, silently, and the tests usually spell every property out, so they do not notice.

- Walked: every public method of every class (declared as a method, or as a property holding an arrow
  function or function expression) and every exported function (declared, or an exported `const`
  holding one, at top level or inside a namespace) under the library trees of `INPUTS_CHAINS`, plus the
  hand-written worker files (`HAND_DIRS`, `HAND_FILES`). The generated worker API classes are not
  walked: they forward a call unresolved and the worker resolves it on the other side of the boundary,
  where `check:worker-api` and the kernel hold it. The hand-written members are walked because they run
  on the calling thread and read the caller's object there (a file name, a download flag). Their
  `Inputs` is the kernel package's (`WORKERS`).
- A parameter names a DTO as `Inputs.<Namespace>.<Dto>`, or `<Namespace>.<Dto>` with the namespace
  imported directly, under any local name the file imports it by (named, namespace and import-equals
  aliases), with or without type arguments, with `| undefined` or `| null`, inside `Omit`, `Pick`,
  `Partial`, `Readonly`, `Required`, `NonNullable` or an intersection, or through a type alias declared
  in the library file or the inputs. A DTO has defaults when it or an abstract parent has a property
  with an initializer.
- Such a parameter must be resolved by the body's opening statements, one per parameter: `const <name>
  = resolveDto(Inputs.<Namespace>.<Dto>, <parameter>)` against that same DTO class, optionally cast to
  its `Resolved` mirror (or an `Omit`, `Pick` or intersection of it, never another DTO's), or
  `return resolveDto(...)`. After it the raw parameter is never read again outside a type position, and
  no parameter is read through `arguments`.
- It fails closed. A DTO with defaults named in any other form - a list, a union of several, inside a
  generic, a tuple or an object type, a name it cannot place - is a finding, since the check cannot
  tell whether the defaults reach it; so is a parameter the type checker gives no symbol, whose reads
  cannot be counted, and an `Inputs.<x>` name that is no class, alias, enum or interface the package
  reaches.
- `resolved-entry.allow.json` lists methods handed a partial object on purpose that resolve it later,
  or pass their options on to a helper that resolves them, each with the reason. An entry that matches
  no method, or whose method now passes, fails.

## worker-parity.mjs

`npm run check:worker-parity` (part of `npm test`); `node scripts/worker-parity.mjs --update` rewrites
`worker-parity.snapshot.json` from the current worker surface.

Each worker package mirrors its kernel by dotted path: every worker method sends a path such as
`assembly.manager.setDocLabelColor`, and the worker thread resolves it by walking properties from the
kernel's root service and calling the method it lands on. A path that does not exist is a runtime
"is not a function" the first time a user reaches it, and the paths are public API persisted in saved
scripts, so the set must not change by accident. All checks are static; no kernel is loaded. The
kernel is walked from its root exactly as the resolver walks it, following `extends` and fields typed
with a kernel class, and the walk is by class name, so a duplicate kernel class name fails.

1. Every path the worker sends resolves in the kernel.
2. Every kernel method is mirrored, outside the `kernelOnly` allow-list.
3. The worker's path set equals the committed snapshot, so any change to the public surface is a
   reviewed diff.
4. The JSDoc on a mirrored method and on a mirrored class reads the same on both sides, indentation
   aside. Docs are authored on the kernel and generated into the worker, whose copy is what downstream
   tooling reads.
5. Every reserved command the worker API sends (a `workerOnly` entry) is declared in the worker
   thread's `ReservedFunctions` (`occt-worker`'s `constants.ts`), so the thread handles it itself instead
   of walking the kernel for a path that is not there.

Signatures are compared too, where both sides declare them: return types after taking off the worker's
`Promise` and normalising the pointer and handle types to one spelling (`normalise`), and parameter
types likewise. An untyped or `any` return has no opinion and is not compared. The kernel imports
`Base` directly while the worker reaches it through `Inputs`, and the worker widens a pointer generic to
`<any>`; neither is a runtime disagreement, so both are normalised away.

`worker-parity.allow.json`, per kernel: `workerOnly` - reserved commands the worker thread handles
itself, never reaching the kernel; `kernelOnly` - kernel methods deliberately not mirrored (the worker
generator reads the same list); `signature` - structural differences that are not defects; `docs` -
paths whose doc cannot read the same on both sides because the worker splits one kernel method into
several.

## check-draw-parity.mjs

`npm run check:draw-parity` (part of `npm test`) fails when a declaration the renderers share has
drifted between them. Each of the three renderer packages owns a copy of `export namespace Draw` in
`draw-inputs.ts`, and has to: a namespace cannot be merged across modules, and the declarations name
types - the renderer's own scene object, its extended Base - that resolve differently in each package.
Sharing the source is not available; holding the copies to each other is.

Every top-level declaration (four-space indented `export type|interface|class|enum|const`) that
appears in more than one renderer must be identical once comments and formatting are taken out, unless
`draw-parity.allow.json` says why. Documentation is deliberately not compared: doc drift is worth
fixing but changes nothing a consumer runs, and failing on it would make the gate noisy enough to be
routed around.

## gen-design-schema.mjs

`npm run gen:design-schema` writes the JSON Schema of the design document from its TypeScript types
(`packages/dev/occt/lib/api/models/design/document.ts`); `npm run check:design-schema` (part of
`npm test`) writes nothing and fails when the schema would change or the release state is
inconsistent.

The types are the source of the format: the runner is written against them, and the schema is what
editors, agents and other languages check a document with before any kernel runs. It is read through
the compiler's type checker, so a mapped type such as the pen commands (every number of a sketch
command allowed to be an expression) resolves to the plain objects it stands for.

- Every interface and type alias named `Design*` or `Sketch*` becomes a definition under `$defs`,
  described by its JSDoc; everything else is written in place.
- An object without an index signature allows no other properties: the format's core is strict, which
  catches typos and invented fields, and its open places are named (`extras`, `extensions`, a filter's
  selector inputs).
- `constraintsOf` adds what `validate` checks beyond the type: a pattern for ids, colours and hashes
  and a least value for counts. A pattern constrains only the string a union may hold and a bound only
  the number, so both sit safely beside a reference to a union. `PATTERNS` are kept equal to the
  checker's by a test. `validate` stays the authority: references, expressions and feature order are
  beyond what a schema can say.

The schema ships in the occt package (`schemas/design-document/`, in its tarball too) and on the
release CDN, whose files never change once a release is cut. While the format is experimental the
schema is `experimental.json` and its `$id` names the release that ships it
(`<CDN>/v<version>/schemas/design-document/experimental.json`), because each release's experimental
schema is its own and documents written against it are not migrated. A released format version has one
address for good (`<CDN>/latest/schemas/design-document/v<major>.<minor>.json`), carried unchanged by
every later release. Editors register the schema under that address from a copy rather than fetch it.

It is also the release gate. Whether the format is released is declared once, in `DESIGN_FORMAT`
(`format.ts`), and three things must agree with it: the `@beta` tag on `OCCTDesign` (on while
experimental, off once released), the file the schema is written to, and the files already published.
A released schema never changes - `published.json` records each by SHA-256 - so a change to the format
after a release needs a new minor.

## gen-ifc-schema.mjs

`npm run gen:ifc-schema` writes the IFC package's schema tables (`packages/dev/ifc/lib/schema/generated/`)
from buildingSMART's EXPRESS files in `packages/dev/ifc/schema/`; `npm run check:ifc-schema` (part of
`npm test`) writes nothing and fails when a committed table is not what its schema generates.

- The EXPRESS files are kept exactly as buildingSMART publishes them: their notice allows translating
  them into another computer language with attribution, and asks consent for changes. The generator
  copies the notice into every table it writes and refuses a schema file that no longer opens with it.
- A table holds, per entity, its supertype, its explicit attributes (name, type, optionality), the
  inherited attributes it derives and its inverse attributes; per type, its definition, enumeration
  values or select options. It leaves out `WHERE`, `FUNCTION` and `RULE` blocks.
- `SCHEMAS` names each source, its output and the constant it exports. A schema is added there and in
  the package's `lib/schema/registry.ts`.
- The generator fails on a type it cannot read and on a name the schema does not define, rather than
  writing a table that would decode files wrongly.

## check-strict-baselines.mjs

`npm run check:strict-baselines` (`verify.yml`) holds every package at zero strict errors. Each package
typechecks with `tsconfig.strict.json`: its build config, whose shared base carries the whole strict
set, with nothing emitted.

It first runs `tsc -b tsconfig.build.json`. Each package's `tsc -p` resolves its siblings through
`paths` into their built `dist`, so without the build it answers about whatever those siblings last
emitted: a worker signature changed and not rebuilt once gave a clean pass here while the real build
failed on a call the new signature rejects.

While the packages were being ratcheted, each carried a `.tsc-baseline.json` recorded by
`tsc-baseline` with `--ignoreMessages` (a message can embed an absolute path into the pnpm store, which
would tie the hash to one machine), and a fresh save had to match the committed file byte for byte, so
the count could only go down. No package has one any more, so the check reduces to "no errors". A
baseline that reappears is still held to the code the same way, so the ratchet can restart for a single
package if it ever must. `tsc-baseline` writes nothing for a clean package, which is read as zero
errors.

## check-tarballs.mjs

`npm run check:tarballs` (`verify.yml`, `publish.yml`) packs every published package the way npm will
and installs the tarballs together into an empty project, the way a user's install resolves them, so a
package that only works inside this workspace fails here: a sibling pinned to a version no tarball
provides, an undeclared dependency, build info that slipped past `.npmignore`, a `workspace:`
specifier. It needs the dists built first (`npm run build-packages`, and each root-published package's
own build) and no network beyond the third-party dependencies.

- A typed probe then imports each package as a consumer would: its root and the extensionless subpaths
  the examples reach into (`<package>/lib/api/inputs`, the occt kernels). An exports map in a published
  manifest would refuse those, so a dist-published manifest must carry none, nor anything else
  `dist-manifest.mjs` drops. There is no runtime import: the packages compile to extensionless relative
  imports for bundlers, which plain Node's ESM loader refuses, and that is how they have always shipped.
- `cad-cloud-sdk`, `create-app` and `mcp` publish from their own root through a `files` allowlist rather
  than a staged dist, so `tsconfig.build.json` does not name them, and nothing packed them until they
  were listed here. Every defect this check grew to catch - a `.gitignore` npm silently strips, a source
  map pointing at sources the tarball excludes - was found in that gap. `create-app` is a bin with no
  types, so it is packed and scanned but not probed.
- npm removes `.gitignore` and `.npmrc` from every tarball whatever `files` says, and reports nothing
  (`NPM_ALWAYS_STRIPS`). A package that needs one ships it under another name and restores it on use.
- A root-published exports map must contain `./package.json`: tooling, the install smoke included,
  reads a package's manifest as a matter of course, and a map without it breaks consumers in a way no
  import of the package reveals.
- `npm pack --json` answers with an array of one entry on npm 11.6 and with the entry itself on a later
  npm; both are accepted, and a third shape fails naming the npm version rather than crashing halfway
  through a release.
- `SECRETS` are shapes that are a credential wherever they appear - deliberately not "a name that sounds
  secret next to a string": the packages are full of `"x-api-key": this.apiKey`, which reads
  configuration, and a check that cried wolf on those would be turned off. Absolute home-directory paths
  fail too, except `/home/web_user`, the emscripten glue's virtual filesystem root.
- The occt tarball must carry its kernels with their glue and typings, the licence notices and the
  design document schemas, and no wasm that `kernels.json` does not list.

## check-openapi.mjs

`npm run check:openapi` (`verify.yml`, `publish.yml`). The committed OpenAPI document
(`docs/static/openapi.json`) describes the API that `@bitbybit-dev/cad-cloud-sdk` targets, and both
carry the version: the document's `info.version` must equal the SDK's package version. A bump that
forgot to regenerate the document, or a regenerated document under an unbumped package, fails here,
before the documentation site publishes the one and the registry the other.

## check-advisories.mjs

`npm run check:advisories` checks every `package-lock.json` and `pnpm-lock.yaml` in the repository
against the GitHub Advisory Database, the database Dependabot raises its alerts from. After `--` it
takes `--severity moderate|high|critical` (default moderate), `--json`, and lockfile paths to check
instead of discovering them.

- It exists because `npm audit` alone is not enough: npm resolves advisories from its own feed, and the
  two have diverged. A project holding nothing but `multer@1.4.5-lts.2` gets "found 0 vulnerabilities"
  from `npm audit` while GitHub holds fifteen advisories against that exact version, which is how
  sixteen alerts once sat open behind a green audit step. Run it beside `npm audit`, not instead of it:
  npm's feed occasionally carries an advisory before GitHub reviews it.
- The advisories endpoint paginates by cursor in the `Link` header and ignores `page`; walking `page`
  re-fetches the first page for as long as a full page comes back, which spends the hourly budget and
  never terminates. A cursor that never ends would be as expensive, so the walk stops at
  `MAX_ADVISORY_PAGES` and fails.
- `affects` takes a comma-separated list, so the tree costs a couple of dozen requests rather than one
  per package; keep `PACKAGES_PER_REQUEST` high. An unauthenticated caller gets sixty requests an hour
  and there are well over two thousand distinct packages; `GITHUB_TOKEN` (or `GH_TOKEN`) raises the
  ceiling to five thousand.
- It refuses to report a clean result it cannot trust: no lockfiles found, fewer than 100 packages
  parsed, or nothing returned by the database is a failed run, since a lockfile layout change, a broken
  parse or a changed API shape would otherwise pass silently. Withdrawn advisories still come back from
  the API and are skipped.
- `advisories.allow.json` lists advisories that are knowingly unreachable or unfixable, each with the
  reason; never one that is merely inconvenient to fix.

## coverage-baseline.mjs

`npm run check:coverage-baseline` compares the last run's coverage and test counts with
`packages/dev/coverage-baseline.json`; `npm run coverage-baseline:save` records them. A refactor, and
above all a change of test runner, must not quietly lose coverage: the same tests should still run and
still reach the same code. The baseline is a floor, not a target - a package whose numbers fell or that
lost tests fails, one that improved is reported and passes.

- It reads only what the suites leave behind (`coverage/coverage-summary.json` and
  `test-results/*.json` beside each package), so it needs a full `npm test` first and never runs a suite.
- Each runner writes one JSON file named for itself into `test-results/`, and the most recently written
  wins: a package that changed runner leaves the old runner's file behind, and reading that would
  report the old run's numbers as this one's.
- A coverage report more than 15 minutes older than the results beside it is the previous run's and
  fails as stale. The two timestamps are used only for that and are not recorded.
- `--save` refuses to drop a package the baseline holds: a partial run would otherwise remove the missing
  packages from the gate silently and for good. A package that should genuinely leave is removed by hand,
  with the reason. The file's `note` says when a re-measure is legitimate.
- `history` keeps the last 24 overall floors (coverage summed over packages, not averaged, plus the test
  count), newest last, so the report can show the trend without a second file.

## test-report.mjs

`npm run test:report` (`verify.yml`, on a red run too, and `nightly.yml`) renders one markdown report over
every test suite and writes it to stdout and, on GitHub Actions, to the run's job summary; that summary
is the public coverage report, so it is written for someone who did not run it. Options: `--root DIR`,
`--expect GLOB` (repeatable), `--title TEXT`, `--baseline FILE`, `--logo PATH`. It exits 1 on any failed
test or missing expected suite.

- Each runner writes its results as JSON into `test-results/` next to the code it tested (jest and
  vitest share one shape, Playwright has its own), with `coverage/coverage-summary.json` beside it.
  Coverage counts only when the same run wrote it: a summary more than 15 minutes from the results is
  ignored.
- `--expect` names directories (one `*` per path segment) whose `package.json` has a `test` or
  `test:coverage` script; each must have left results, so a suite that silently stopped running is
  listed and fails the step.
- Suites are named by their path from the working directory (the repository root in CI), so a report
  over one unit still says which unit it is.
- `--baseline` shows what each suite moved against the recorded floor, and the floor's history as
  sparklines (each scaled to its own range, so a flat run reads as flat). Overall coverage is summed
  across suites, so one large package cannot be averaged away by several small ones.
- `--logo` is a repository path; the image URL is built from the run's own commit, so the report always
  shows the logo that commit carried and nothing is fetched from elsewhere.
- The banner is the scaffolder's greeting, as text in a code fence rather than an image, so it survives a
  terminal, a raw log and a summary page alike.
- Every percentage carries a coloured dot for its band (`BANDS`: below 30% barely begun, below 50% a
  fraction of the surface, below 70% genuinely tested with room left, above that where a package should
  end up), because a column of them is scanned rather than read. Yellow is the closest to a pale green
  available. A dot rather than coloured text, because colour in a run summary has to be typeset as
  mathematics, which reads as a formula to a screen reader and is lost in a log. Bars are block
  characters for the same reasons, with the number beside them.
- The codebase table counts a line as code unless it is blank or opens with a comment marker, and
  separates generated source (a `generated by` or `do not edit` marker near the top) from hand-written,
  because counting the assembled inputs, the worker API layer and the SDK types as authored would
  overstate both the code and how much of it is tested.
- The quality signals are each read from the file the owning tool writes, and absent when that file is
  not there. Deliberately nothing about dependency advisories: a public report is the wrong place to
  enumerate unpatched versions.

## fetch-kernels.mjs

`npm run kernels:fetch` (both workflows, after the install, and the occt package's `build-p` through its
`fetch-kernels` script) fetches what is missing and verifies what is present; `npm run kernels:check`
verifies only and fails if anything is missing or differs.

The three OCCT wasm kernels (about 35 MB each, a new set on every kernel rebuild) are not tracked:
`packages/dev/occt/kernels.json` records, per variant directory, the content-hashed file name the
emscripten glue references, its size, its SHA-256 and where it is published. The kernel build writes the
manifest when it deploys a fresh wasm, so on a machine that builds the kernel the file is already there
and this is a no-op; on a clone it downloads. The SHA-256 decides: a file with the right hash is kept, a
file with another hash is an error and is never overwritten (the deploy folder is the source of truth,
and a mismatch means the manifest was not updated), and a missing file is downloaded, verified and
renamed into place. The glue must name the manifest's file. An entry without a url was built but not
published - the build writes the entry and publishing fills in the url - which is fine where the file is
present and a hard stop naming the file anywhere else.

## publish-packages.mjs

`npm run publish:packages -- [--tag latest|rc|beta|alpha|next] [--dry-run]`, run by `publish.yml`.
Publishes the packages to npm in dependency order, resumably. The packages pin each other with exact
versions and the registry checks nothing about a dependency's existence at publish time, so a dependent
published before its dependency fails to install (ETARGET) for every user until the dependency lands -
and after 72 hours a published version cannot be taken back.

- The packages and their order come from the manifests alone: every non-private `packages/dev/*`
  package, in tiers of packages whose siblings are all placed, the same graph the build follows. All
  must share one version.
- A version the registry already has is skipped, so a run that stopped half way is simply run again.
- After every tier, the last included, the registry is polled until each package resolves: a fresh
  publish can lag the registry's read path, and skipping the wait on the final tier once raced the
  install smoke that follows seconds later, failing a publish that had worked.
- Dist-published packages publish `dist/` (the manifest `dist-manifest.mjs` wrote, whose version must
  match the source); `cad-cloud-sdk`, `create-app` and `mcp` publish their root through their `files`
  allowlist and their `prepublishOnly` build.
- Authentication comes from where it runs: npm trusted publishing in `publish.yml`, the logged-in npm
  locally; `--dry-run` publishes nothing and is the rehearsal.
- The dist-tag and the version must agree, and neither mistake is recoverable: a prerelease publishes
  under its own channel (`-rc.0` to `rc`, `-beta.1` to `beta`), so it can never become everyone's default
  under `latest`, and a release version goes only to `latest`, because a version cannot be republished
  and moving a dist-tag afterwards needs a granular token or an interactive login, which OIDC does not
  provide.

## lib/surface.mjs and lib/kernel-surface.mjs

`lib/surface.mjs` is the one copy of the TypeScript surface the checks and generators walk - which files
count as source, how they are parsed, how classes are found by name. The worker generator, the parity
check and the documentation check each once carried their own copy and drifted in what they skipped.
How the class tree is walked from its root stays with each script on purpose: the documentation check
follows type names, the parity check follows `extends`, the worker generator refuses `extends`.

- `sourceFiles(dir)` returns the sorted `.ts` files under `dir` that are not tests, declaration files,
  dependencies, build outputs, dot-directories or test support (`__mocks__`, `__test__`). The inputs
  fragment directories are skipped unless `{ fragments: true }`: a class walk wants each DTO once, from
  the assembled file, while the documentation check wants the fragments, where DTOs are authored. A
  missing directory is an empty surface.
- `parse(file)` parses each file once per process.
- `HAND_DIRS` and `HAND_FILES` are the hand-written part of the four worker packages (OCCT, JSCAD,
  Manifold and IFC): the members the worker generator merges into its generated classes and the init
  classes it does not generate. They run on the calling thread, so the documentation check audits them
  and the resolved-entry check walks them.
- `INPUTS_CHAINS` names, per package with inputs DTOs, the packages whose inputs its `Inputs` namespace
  re-exports, its own first: a DTO name declared in two of them (the renderers' `Draw`) means the nearest.
- `isPublic` excludes private, protected and static members; `jsdocOf` returns the last JSDoc block
  directly above a declaration, as written.
- `classesUnder(dirs)` maps every class name to its first declaration and records the files of any later
  one in `duplicates`: class names are unique per package, and a walk by name has to be told when they
  are not.

`lib/kernel-surface.mjs` walks a kernel from its root class exactly as a dotted path is resolved at run
time and returns, per dotted prefix, the API class with its class-typed properties and its public methods
(path, doc, parameters, return type). The worker and DTO metadata generators emit from it. It throws on
what those generators cannot emit: a class that `extends` another (the worker classes are flat), a method
without a return type annotation, with type parameters, or with an optional, default or rest parameter.
