## This template: IFC family house

A two-storey family house written as an IFC4 building model with `@bitbybit-dev/ifc`, drawn with Manifold and exported to STEP with OpenCascade. Before changing how the house is written, read the IFC guide of the Bitbybit CAD MCP: `get_guide` with the topic `ifc`, then `ifc-order` and `ifc-mistakes`. Every `ifc` method is described there by its dotted path (`describe` with `ifc.walls.add`) and has examples (`get_examples` with `ifc.doors`).

- `src/house/house-plan.ts` is the house as data and the place to make most changes. The model is in metres (`lengthUnit` metre), so every length here is in metres; plans are `[x, y]` on a storey with Z up from its floor, never Y up. `WALL_RUNS` lists the walls run by run with the joins between them, `WINDOWS` and `DOORS` place a type in a wall by its id, `offset` along the wall's axis from its start, `SLABS`, `ROOF`, `CARPORT`, `ROOMS`, `TERRAIN_OUTLINE`, `TREES` and `PROPERTY_SETS` the rest. Every element has an `id` of its own that later entries refer to; ids are unique in the model.
- `src/house/details.ts` generates the details from the plan: cladding boards cut around each facade's openings and gathered into an assembly per facade (`houseAssemblies`, `userDefined` with an `objectType`), flashings, window surrounds and sills, copings, the solar array, the stair, rainwater pipes, the canopy, the carport frame, glass rails and the study's glazing, all as members and beams with their own materials. A detail is placed in its storey's frame, `[x, y, z]` with z up from the storey's floor.
- `src/house/build-house.ts` writes the plan into a model in the order IFC needs: the model and storeys, materials and layer sets, walls with their joins, slabs, window and door types and their placements, the roof and the carport, the details and assemblies, the site, rooms, property sets, and quantities last. `HouseAuthor` takes the IFC API itself (`HouseIfc`), so it runs unchanged on `bitbybit.ifc` in the browser and on the in-process library in the smoke. Every call that changes the model assigns the model it returns; a call whose result is dropped changes nothing.
- `src/scene/draw-house.ts` builds the model's recipe (`ifc.geometry.recipe`) with Manifold (`manifold.recipes.build`, `adjustZtoY` so the Z-up model stands up in Three.js) and draws one mesh per element in the colour of its material, read from the root's `rgba` tag; the root's `globalId` ties a mesh to its element and its layer (a storey, the roof or the garden).
- `src/export/step-export.ts` starts the OpenCascade worker on the first STEP download only and calls `ifc.geometry.toStep` with `facetedMeshes`, so the trees, which are triangle meshes, are written as faceted solids that every CAD tool opens rather than as tessellated geometry.
- `src/workers/` holds the three workers. The Manifold and OpenCascade kernels load their WebAssembly from the Bitbybit CDN folder of the installed version; the IFC library needs none.
- `scripts/smoke.ts` writes the house twice on the in-process library and prints one JSON line: `template`, `schema`, `elements`, `walls`, `windows`, `doors`, `rooms`, `netArea` (square metres), `recipeRoots`, `emptySolids`, `authorMs`, `manifoldMs`, `ifcBytes`, `deterministic`, `stepBytes`, `stepMs` and `problems`. It exits 1 when the house lacks walls, windows, doors, slabs, the roof, members or the site's geographic elements; when an element's geometry cannot be described (`geometry.unsupported`); when the rooms differ from `ROOMS` or one has no area; when Manifold builds nothing for an element; when the two runs write different bytes; or when the STEP export, built on the in-process OpenCascade kernel, lacks its header.

Commands:

- `npm run dev` serves the viewer at http://localhost:5173
- `npm run build` typechecks and bundles for production; `npm run typecheck` and `npm run lint` run alone as well
- `npm run smoke` typechecks, lints, then writes the house headlessly and prints the summary line. The smoke types the in-process IFC library as the same `HouseIfc` the browser code sees, through one `inProcess` cast, and awaits every call, so `HouseAuthor` runs exactly as it does in the browser.

To add a room: add an entry to `ROOMS` with its own id, its storey, number, name, outline and height, and run the smoke, whose room count follows `ROOMS`. To add a window: add a window type to `WINDOW_TYPES` if the size is new, then an entry to `WINDOWS` with its own id and name, its wall, its type, its `offset` and its `sill`; the facade's cladding is cut around it on its own. A window or door cuts its own opening in its wall; never add an opening for it as well.
