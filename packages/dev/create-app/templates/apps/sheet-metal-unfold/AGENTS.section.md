## This template: sheet-metal unfold

A sheet-metal channel that is built in the browser on the open-source packages and unfolded on CAD Cloud, because the unfold is a Pro algorithm that exists only there. Two packages in one npm workspace: `frontend/` (Vite, Three.js, the OCCT kernel in a worker) and `backend/` (Express, the CAD Cloud SDK, the key).

- `frontend/src/model.ts` is the open-source geometry. `centreLine` is the sheet's centre line through the channel's cross-section as a sharp polyline; `buildModel(occt, params)` rounds every corner of it with `fillet2d` at the mid-sheet radius (inner radius plus half the thickness), then sweeps a thickness-by-depth rectangle along it with `pipe`. A swept sheet has concentric bend arcs and one thickness everywhere, which is what the unfold needs. `mounting` then adds two holes through the base and a slot through each flange, on the flat sheet between the bends and never in a bend zone, leaving out any feature that does not fit with its margin (`MOUNTING`); the slot is a rectangle rounded to a stadium. The part's volume is exactly the thickness times the centre line's length times the depth minus what those features remove (`removedVolume`, analytic because every feature goes through flat sheet), which is what the smoke checks. `flatLengthEstimate` is the K-factor estimate of the developed length, computed without any kernel, so the page shows a number before the cloud answers and the difference afterwards.
- `frontend/src/flat.ts` reads the cloud's report: bend lines to draw over the flat pattern, and `summarize` for the facts. `toScene` maps the report's Z-up frame onto the ground plane the flat STEP is loaded onto with `adjustZtoY`.
- `frontend/src/main.ts` is the wiring: scene, kernel, debounced rebuilds, the part and flat views (the flat pattern drawn one millimetre above the ground so it never fights the ground plane for pixels), the unfold call and the downloads, the sheet in a brushed steel material under a room environment. `cameraOptions` gives the orbit camera explicit distance limits from the scene size and leaves its sensitivities at their base values: the engine's defaults scale zoom and pan by the scene size although both already follow the camera's distance, so a scene this large would jump a third of the way in per wheel notch.
- `frontend/src/cloud-access.ts` is the access state: `accessFromResponse` turns the backend's answer into `ready`, `locked` (503 with `NO_API_KEY`), `unreachable` or `error`, and `renderAccess` shows the locked state with the CAD Cloud page, the Studio keys page and the `.env` line. That state is part of the app: keep it working and keep its links current.
- `backend/src/app.ts` is the whole server: `GET /api/health` and `POST /api/unfold`. Without a gateway it answers 503 with the code above. With one it uploads the STEP text, calls the Pro unfold, waits for the task, fetches the flat STEP and returns it with the report from the task metadata. `backend/src/cloud.ts` is the gateway over the SDK: uploads, tasks and results through the SDK's endpoints, the unfold through the client's `request` method because the SDK has no wrapper for the Pro endpoints yet.
- Smokes: `frontend` (typecheck and lint, then the kernel, typed as the browser's `Occt` through one `inProcess` cast and awaited, builds three channels and checks each is a valid solid whose volume is the thickness times the rounded centre line times the depth minus the mounting features, with the declared extents, the estimate is below the outer lengths, and the pure cloud code maps a canned report and the three access states; The kernel is loaded in-process from `node_modules`, the same WebAssembly the browser runs inside a worker; its content-hashed `.wasm` is found beside the loader rather than spelled out.) and `backend` (typecheck and lint, then the app is started twice on a free port: without a key it must answer 503 with the code and both links; with a fake gateway it must call upload, unfold, wait, downloads and fetch in that order and pass the report, the flat STEP and the downloads through). Neither needs a key or a network.

Commands, from the project root:

- `npm install` installs both workspaces
- `npm run dev:backend` serves the backend on http://localhost:3000; `npm run dev:frontend` serves the page at http://localhost:5173 with `/api` proxied to it
- `npm run smoke` runs both smokes, each typechecking and linting first; `npm run build` builds both; `npm run typecheck` and `npm run lint` run across both

## What needs CAD Cloud and where to get it

Only the unfold. Building the part, measuring it, estimating the flat length and downloading the part as STEP run in the browser on the MIT packages; nothing of Bitbybit's is in that loop. The unfold (`POST /api/v1/cad/pro/unfold/solid`) is a Pro algorithm available only on [CAD Cloud](https://bitbybit.dev/cad-cloud): it returns the flat pattern as STEP and glTF and a report with every bend's angle, radii and allowance. That is the one call in `backend/src/cloud.ts`.

- The plan needed: any CAD Cloud plan. The key needs the `cad`, `files` and `tasks` scopes. Every unfold is one metered task on the key's account.
- Where the key comes from: [Bitbybit Studio](https://studio.bitbybit.dev/keys/billing), which also lists the tasks this app ran.
- Where the key goes: `backend/.env` as `BITBYBIT_API_KEY=...`, which `.gitignore` already ignores. Never in `frontend/`, never in a prompt, never in a log.
- Without a key: the backend answers 503 with `NO_API_KEY`, the page shows the access state with the links above, and everything else keeps working. Do not move the unfold call into the browser to avoid the backend: that would put the key in the client.
- Do not replace the cloud unfold with a browser approximation and present it as the flat pattern: the K-factor estimate is shown as an estimate, on purpose. A one-line manual check with a real key against staging is part of releasing this template, because the fake gateway proves the plumbing, not the algorithm.
